# Encrypted connections to the hub (optional)

Status: implemented behind `kaptyorka tls`; off by default. The real hub was not touched.

## The problem

The hub serves plain http on the LAN (`http://<lan-ip>:8765`). Device tokens (every request's
`Authorization` header), invite redemptions (which return a token and a signing secret), page
links (`#t=<token>`, kept in the browser, but the page then sends the token as a header) and the
page's GitLab session cookie all cross the network in clear text. Anyone on the same network
can read them and take over a machine or a person's account.

## Research

| Source | What it says | What we take |
|---|---|---|
| Syncthing, [device IDs](https://docs.syncthing.net/dev/device-ids.html) and [security](https://docs.syncthing.net/users/security.html) | Each device makes a key and a self-signed certificate at first start. The certificate is "little more than a container for the public key", and there is no CA. The device ID is the SHA-256 of the DER certificate. It is exchanged out of band (typed or pasted). On connect each side hashes the peer's certificate and drops the connection unless it is in its list. | Pinning a fingerprint that arrives out of band is a proven way to secure a LAN tool without a CA. |
| Python [`ssl`](https://docs.python.org/3/library/ssl.html) | `CERT_NONE` accepts any certificate. `check_hostname` must be off before `CERT_NONE` is set. `getpeercert(binary_form=True)` gives the DER bytes after the handshake. `create_default_context(cadata=...)` trusts exactly the certificates it is given. From 3.13 `VERIFY_X509_STRICT` is on by default. | `http.py` checks the fingerprint right after the handshake, before any byte of the request is sent. The shim's httpx client has no hook after the handshake, so it trusts the pinned certificate alone (`cadata`), with strict mode cleared and partial chains allowed. |
| uvicorn [settings](https://uvicorn.dev/settings/) | `ssl_certfile` and `ssl_keyfile` (default `ssl.CERT_NONE` for client certificates), or an `ssl_context_factory`. | The hub runs a second `uvicorn.Server` with `ssl_certfile`/`ssl_keyfile` on the TLS port, in the same process and event loop. It has `lifespan="off"`, so the tick loop and the MCP session manager start once. |
| [mkcert](https://github.com/FiloSottile/mkcert) | Creates a local CA, installs it in the system and browser trust stores, and issues certificates for any names or IPs. Its warning: the CA key "gives complete power to intercept secure requests from your machine". Other devices install only `rootCA.pem`. | The hub makes the same kind of local CA (on the hub only, `ca.key` mode 0600, never copied). Browsers may install `ca.crt` to stop the warning. Machines never need it. |
| Home Assistant, [HTTP](https://www.home-assistant.io/integrations/http/) and [securing](https://www.home-assistant.io/docs/configuration/securing/) | Certificate and key paths in its HTTP settings, Mozilla TLS profiles. For remote access it recommends its cloud, Let's Encrypt with Duck DNS, or a VPN. It does not recommend self-signed certificates. | A real CA needs a public DNS name, which a LAN hub usually lacks. So the hub does not depend on one, but a hub behind a real certificate keeps working: an https URL with no pins is checked against the system CAs. |
| Gitea, [HTTPS setup](https://docs.gitea.com/administration/https-setup) | `gitea cert --host` makes a self-signed certificate. `PROTOCOL=https` in `app.ini`. `REDIRECT_OTHER_PORT` and `PORT_TO_REDIRECT` keep a plain port that only redirects. | The same shape: a generated certificate, https on one port, and the old http port answering "moved" (a browser's plain GET is redirected). |
| Tailscale, [HTTPS](https://tailscale.com/kb/1153/enabling-https) and [what it is](https://tailscale.com/kb/1151/what-is-tailscale); WireGuard | Encrypts the network instead: WireGuard tunnels between devices. It needs an account, a client on every device and the coordination service. Its HTTPS certificates come from Let's Encrypt for `*.ts.net` names, which are published in Certificate Transparency logs and last 90 days. | A good alternative for teams that already run it (section "Alternative" below). As kaptyorka's only answer it is too heavy: a new agent and account on every Jetson and laptop, and a third party. |
| GitLab, [OAuth provider](https://docs.gitlab.com/integration/oauth_provider/) | An application's Redirect URI is set under avatar > Edit profile > Access > Applications, a group's Settings > Applications, or Admin > Applications. One URI per line. | After the switch the page's sign-in sends `https://<hub>:<tls port>/auth/gitlab/callback`. That line must be added to the GitLab application before `tls on` (exact matching is standard OAuth behaviour, not quoted from that page). |

## Design and why

1. **The hub makes its own CA and a server certificate signed by it.** Both are made with `openssl`, which is on every Ubuntu, Jetson and macOS, so there is no new Python dependency and only the hub machine needs it. The CA is RSA 2048, 10 years, `CA:TRUE`. The server certificate is RSA 2048, 825 days, `serverAuth`, with the computer's name, `localhost`, 127.0.0.1 and the LAN address in subjectAltName. 825 days is Apple's limit for TLS server certificates, so Safari accepts it too. The files are in `~/.kaptyorka/tls/`, with keys at mode 0600.
2. **Machines pin the server certificate's SHA-256; they never trust a CA.** It is the same idea as Syncthing's device ID. It reaches them without a gap:
   - **A new machine:** the invite link carries it: `https://<hub>:<tls port>/i/<code>#sha256=<64 hex>`. The fragment never goes to the server. `kaptyorka join` checks the hub's certificate against it before it sends anything (the invite is not spent on a mismatch).
   - **A machine already joined:** the fingerprint comes in the heartbeat answer, which it already receives. The announcement is HMAC-signed with that device's own signing secret, the one launch orders already use (`orders.py`). Someone between the machine and the hub cannot change it without that secret.
   - **The one weak spot, said plainly:** the secret itself was handed over at join time over plain http. Someone who recorded that exchange could forge an announcement. That attacker could already take the token, so https removes that risk from the switch onwards, and a machine joined from an https link never had it.
   - **The `kaptyorka join --hub --token` path:** it takes `--fingerprint`.
3. **The move is in three steps, each checked:**
   - `kaptyorka tls on` makes the certificate and adds https on the TLS port (default: hub port + 1) beside http. Every heartbeat answer then says `use: https`, with the https address, the pins and the plain address. A bridge moves its saved hub address to https only after a test call there with the pin works. It keeps the old one as `hub_plain`. Every other client (CLI, hooks, status line, shim) reads the address from that config, and the long-running shim re-reads it on each reconnect.
   - `kaptyorka tls status` lists each machine with the scheme and pins it reports in its facts.
   - `kaptyorka tls only` refuses while an online machine is still on http, unless `--force`. Then plain http serves only this computer itself (127.0.0.1: the manager, whose config is loopback). A browser's plain GET is redirected to https. Anything else gets a 403 that names the new address and says to get a new invite link.
4. **A machine that was off during the move needs one `kaptyorka join <new link>`.** Telling it the fingerprint over plain http would be trust on first use, and an attacker could answer instead. Its old http token had been crossing the network in clear anyway. `tls status` shows who is behind, so the admin can wait before `only`.
5. **Rollback:** `kaptyorka tls off` reopens plain http and the announcement says `use: http`. Bridges move back to their `hub_plain` after a test call works there. A second `kaptyorka tls off` (refused while an online machine is still on https, unless `--force`) stops https. The certificate is kept for a later `on`.
6. **Rotation:** `kaptyorka tls rotate` makes the next certificate and announces both pins. A second `rotate`, once `tls status` shows every machine with the new pin, swaps the files and restarts the hub. A machine that missed it needs a new link. Browsers with the hub's CA installed see no change, because the CA stays. The admins get one message 30 days before the certificate ends.
7. **Default:** plain http stays the default. `tls.state()` is "off" without a `tls` key in hub.json. Old `http://` invite links work as before. An https hub that has a real certificate and no pins is checked against the system CAs as usual.

## Every place that talks to the hub

| Client | Path | After the switch |
|---|---|---|
| Bridge (heartbeat, poll, ack, worker, skills, rekeyed) | `http.py` with `self.cfg["hub"]` | Moves itself (`tls.follow`), then pinned |
| CLI admin commands, `status`, `doctor`, `page`, `gitlab status` | `http.py`, config `hub` | Pinned from the config; `gitlab status` prints both redirect URIs during the move |
| Hooks (`hook.py`, `offhub.py`, `optin.py`, `overnight.py`) | `http.py`, `load_config(cwd)` | Pinned from the config |
| Status line refresh (`hubstate.py`) | `http.py` | Pinned from the config |
| MCP shim (`shim.py` `Relay`) | httpx2 | Re-reads the address on each connect (`tls.current_url`); `verify=tls.client_context(...)` trusts only the pinned certificate |
| Manager session | its own config, `http://127.0.0.1:<port>` | Loopback: still served in `only` |
| `join` (invite, `--hub/--token`) | `http.py` with explicit pins | Pins from the link or `--fingerprint` |
| Links the hub hands out (`hub_url`, invites, sign-in callback) | `tls.base_url` | https on the TLS port, invites with `#sha256=` |
| Invite redemption's answer `hub` | the request's own address | A machine joining over http stays there and follows the announcement |
| GitLab API and OAuth token calls | `gitlab.py`, `signin.py` | Not the hub; unchanged |

## Alternative: encrypt the network instead

If the team already runs Tailscale or WireGuard between every machine, the hub can stay on plain
http on the tunnel's addresses: the tunnel encrypts and authenticates every packet. That needs no
change in kaptyorka, but an agent and an account on every machine, and it covers only the
machines inside the tunnel. kaptyorka's own TLS works on any LAN without either.

## What was verified by running and what is only designed

**Run, in `tests/test_tls.py`.** A sandbox hub was used each time: the real `openssl`, the hub's own two listeners (`tls.servers`) on free ports, and the test's temp home.
- A browser-like client with the hub's CA installed and hostname checking on fetched the page.
- Pinned calls worked, a wrong fingerprint was refused, and an https call with no pin was refused by CA checking.
- An https invite with the fingerprint worked, and a link whose fingerprint was changed was refused without spending the invite. An old http invite still worked.
- Announce, follow, only, rollback and off ran on the real listeners. Forged, replayed and wrong-secret announcements were refused, with a fake time for the age check.
- In `only`, plain http still served loopback, redirected a browser's GET and refused the rest.
- `only` and `off` waited for machines that had not moved.
- The MCP shim's tool call over https with the pin worked, and with a wrong pin no call was made.
- Rotation ran with a restart of the listeners.
- A real `Bridge` heartbeat moved the config to https and reported it in its facts.
- The expiry notice was sent once.
- Defaults: off, no announcement, http links.

**Only designed, not run.**
- The switch on the real hub and the real systemd restart (`service.restart`).
- Real browsers (Chrome, Firefox, Safari) accepting the self-signed certificate or the installed CA.
- GitLab sign-in with the https redirect URI.
- macOS's LibreSSL `openssl` with these options.
- A machine on another subnet.
