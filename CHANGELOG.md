# Changelog

## 0.9.33 (unreleased)

- **Working together.** Sessions that wrote to each other both ways in the last 30 minutes, and a session with the workers it started, form a group (linked sessions join one group; it ends when they go quiet, a worker stays with its boss while it runs). Home shows a **Working together** block under the manager: per group a title line (project or "mixed", how many sessions, last active) and its sessions on one line, a worker under its boss; a message between them lights the line once (not with reduced motion). The title line opens the group's conversation, read only, with "from → to" when there are more than two. A session's chat header shows **Working with** and its partners; a click opens one. The hub computes the groups (`groups` in `/api/feed`) and serves a group's messages at `/api/groups/<id>/messages`. Privacy is the hub's: a member's groups hold only sessions they may already see, a partner they may not is counted as "another session" with nothing of it, and two visible sessions are never joined through a hidden one. The manager is never in a group, since it talks to everyone and would join all work into one.
- **Your sessions by machine.** A member's list, and an admin's Mine, put sessions under one foldable header per machine (`account@computer`, team machines tagged **Team**) with count and unread count, remembered per browser; with one machine there is no header.
- **Warnings take one line, not half the chat.** Each blocking warning was its own full-width bar over the chat (several bridges offline or failed workers stacked up, and long text wrapped to many lines on a phone). Now they sit behind an amber warning sign with a count in the top bar, which opens the full list with each command and Copy. Over a chat there is at most one line, only for that chat's own machine, with its command, "+N more" and a dismiss kept per browser (the list's **Show again** brings it back). The line floats over the messages, so nothing moves when it appears. Following GitHub Primer ("do not display more than one banner on a single page at the same time"; single-line banners keep actions and dismiss on the same line) and the status-sign-with-popover of Vercel and Linear.
- **The list holds still.** Every change redrew the whole session list, so each row was made anew (motion restarted, a hover dropped); a session missing from one 2-second update vanished and came back; a new message made the "is working" line rise in again. Now a row that did not change keeps its place on screen, a session or group missing for up to 2 updates stays as it was, a session whose name changes keeps its open chat and draft, and the "is working" line is drawn once.

## 0.9.32

- **Stuck sessions are caught.** A session that ended its turn while a background task ran a wait loop that never ended sat for almost 17 hours with the page saying "Working". The bridge now reports, for Claude Code on Linux, each busy session's live background tasks (its child shells writing to Claude Code's task output files: id, command, how long since they printed) and when the session itself last wrote (messages delivered to it do not count). The hub calls a session stuck when a background task has printed nothing for 30 minutes, or when a busy session has written nothing for 30 minutes. It then asks the session once to check (a finished turn reads it at once), and at 60 minutes tells its person, a worker's boss and the manager how to stop it; the manager hears it once more 30 minutes later. Idle sessions, older bridges and other tools are never judged. Checked on real `claude --bg` sessions (Claude Code 2.1.331): the session file's status is `shell` while a background task runs after the turn, a background Bash call's `timeout` is not enforced, and a message to a finished turn starts a new one.
- **The page shows "Background task" instead of "Working"** for a session whose turn is over while its background task runs, and an amber "Silent 1 h" or "Stuck 2 h" for a stuck one.
- **Overnight mode wakes a session stuck on a silent task.** Its Stop hook lets a session with background work wait for it, so a task that never ended kept it asleep until the 16-hour cap. The bridge now asks it, once per silence, to check the task.
- **Overnight mode no longer turns on from words about a past night** ("the overnight task results", "last night", "it ran all night"), unless the prompt also asks for tonight ("until I'm back", "while I sleep", "by morning", "overnight task:"). The morning report lists only the current night's notes, not those of earlier nights in the same session.
- **Team machines put every session on the hub.** On a team machine (an account the hub counts as shared) every session, in any folder and any tool, is on the hub without `/hub team`; in a folder that is no team project it joins as a coordinator, so nothing of its folder leaves the machine. `/hub off` still takes one session off, and the next one starts on again. The start guide says the session is on the hub and how to take it off. Personal machines are unchanged. The bridge keeps the hub's `shared` answer in `~/.kaptyorka/team.json` for the tools' shims and hooks.
- **OpenCode 2 sessions stay on the hub while their window is open.** The bridge guessed each OpenCode 2 window's session as the newest chat in the window's folder updated since the window started. That missed a chat reopened with `-s`, `-c` or the session list (its last update was older than the window), a window started as `opencode <folder>` from another folder, and the second of two windows in one folder. Such a session was seen only for 30 seconds after each of its own kaptyorka tool calls, so a message sent later waited for its next turn instead of being pushed, and names flipped between `proj-a` and `proj-a-2`. Now kaptyorka's TUI plugin writes which chat each window shows to `~/.kaptyorka/opencode-open/<pid>.json` (when it changes; removed when OpenCode quits), and the bridge lists exactly those, idle or not. A window started before this update still gets the old guess until it is restarted. Checked with real OpenCode 2.2.5 and 2.3.2 windows in a sandbox (two windows in one folder, resumed chats, `opencode <folder>`, quit and kill); the session list's response is the same in both versions.

## 0.9.31

- **A busy machine no longer shows live sessions offline for a moment.** The bridge rebuilt its machine facts (each tool's login check, machine use, git state) once a minute inside the loop that reports sessions; on a loaded machine that took long enough to push a session report past the hub's 30-second online window. The minute rebuild now runs beside the report; the first build and one the hub asks for still run at once. This was the intermittent slow-test failure.
- **Overnight mode no longer turns on from a subagent's report.** Claude Code hands a session its subagents' reports, background task notices and other sessions' messages as prompts, before the transcript says who sent them; a report that named overnight mode turned it on. These texts never count as the person now.
- **Session names on the page match Claude Code.** A Claude Code session you named (`/rename` or `claude -n`) shows that name; an unnamed one now shows Claude Code's own title instead of its automatic `<folder>-<2 characters>` name, which meant nothing and changed on every resume. The automatic name still shows while a session has no title yet. The bridge tells them apart by the session file's `nameSource` field (`derived` for the automatic name, `user` for `-n` and `/rename`; checked on Claude Code 2.1.329 and 2.1.330), so a worker named `proj-a-w3` keeps its name; the manager always keeps its own. An agent can no longer `send` to a session by its automatic name.
- **Forgotten sessions fold into an Idle group.** Sessions that did nothing for over a day (such as two terminals left open for a month) move from Home's list into one **Idle** group at its end, folded at first and remembered per browser, each row saying "idle N hours" (under 48 hours) or "idle N days". They stay online and reachable; nothing else changes, and the group's count is of the sessions in it. Never the manager, a worker or a background job (those stay in Background). The bridge reports each session's last activity in its session report: Claude Code's transcript time (from the check it already does for titles, no extra reads) and Codex's thread `updatedAt`; OpenCode and Cursor send none and never fold. A bridge older than this sends none either. The page feed now also marks the hub's workers.
- **Workers start on team machines.** A machine joined as if it were a person (a lab or robot box) became a team machine with `kaptyorka machine team --from <name>`, but no worker could start there: its account did not count as shared, so the hub treated it as someone's private laptop and its bridge refused other people's orders. Now a team machine's accounts always count as shared, and anyone with the write role in a project may start a worker on one (`work(project, task, machine="jetson-1")`); a team machine hidden from a person stays off for them, admins may use any, and a device merely marked shared still needs a grant. That one command is the whole setup. `kaptyorka machine team --undo <name>` turns it back into a person (member role; refused while another person's worker runs there).
- **A session on a team machine may ask for a worker.** Its boss is that session, its person the team machine, which needs the write role in the project itself. A worker on a team machine still may not start, adopt or close workers, also when its boss is a session of that same team machine. The manager never starts workers itself (`work` refuses it); asked through the manager, the worker's boss stays the session that asked.
- **Workers close by themselves.** When its task is done, a worker reports to its boss and calls `close_worker` with its own name (its first message says so); and 10 minutes after its boss session really ended (the boss's bridge is online and no longer lists that Claude Code session; offline is not ended, and a boss in another tool never counts). Only Claude stops; commits, branch, worktree and files stay. The boss gets one line naming why and what it left (branch, number of uncommitted files, folder), read by the bridge at the close; when the boss ended, the person's page gets it too. Never for a worker whose boss is the page, nor while overnight mode is on in it: the bridge now reports which sessions are in overnight mode and refuses such a close itself. A worker on an older bridge (which does not report overnight mode) is never closed by the boss rule.
- **Claude Code workers stay in the folder the hub chose.** Claude Code 2.1.330 keeps a `--bg` session out of its start folder, or moves it into `.claude/worktrees/` (no team project there, so it left the hub). The bridge now starts each Claude Code worker with its own `--settings` (`worktree.bgIsolation: none`, `EnterWorktree` denied); nobody's Claude Code settings change, and kaptyorka still makes its own worktree when the folder is busy. Checked with a real Claude Code worker in a sandbox.
- When a worker cannot start on the machine named, the answer says in one line what is wrong and what to do: someone's own machine (an admin runs `machine team --from`), no folder for the project (clone it, or give the team machine a role so its bridge finds `~/<project>`), bridge offline (`kaptyorka doctor --fix` there), a shared account without a grant, or no machine by that name you may use.

## 0.9.30

- **Overnight tasks (Claude Code).** A prompt that says "overnight task", "run this overnight", "while I sleep" or similar, or `/hub overnight`, turns on overnight mode for that session; it shows one line and the night rules, which the developer confirms or changes in words ("you may move the motors" allows that one class for this task). Night rules: everything allowed except admin rights (`sudo`, `su`, `pkexec`, `doas`), force push or history rewrite on shared branches (`main`, `develop` or the project's list), deleting system folders, the home folder itself, other users' homes or protected folders (also through symlinks, and with Write and Edit), and commands on the developer's hardware list (nothing built in). A command the hook cannot read is blocked and noted. Questions with options are denied with "take the recommended option and note it"; permission prompts inside the rules are allowed and outside them, or from the developer's own ask rules, skipped and noted; a stop gets "continue" at most 3 times in a row; a crash is resumed with `claude --resume` in tmux at most twice; a usage limit or API error is waited out for at most 6 hours. Only documented hook decisions; deny and ask rules keep priority, nothing skips permissions. It turns off when the person types again (hub and kaptyorka messages never count: the bridge remembers what it delivered), with `/hub overnight off`, when the task is done, or after 16 hours. The morning report and the decision log stay on the machine (`~/.kaptyorka/overnight/`, 0600, secrets dropped); a team session also sends the report to the person's own hub page, and a team or project rule clash as a short fixed-text event that the manager passes on once. Claude reports clashes with `kaptyorka overnight clash` rather than the `conflict` tool, since `conflict` stores rule text on the hub and a personal session must send nothing there. Codex, Cursor and OpenCode: not yet. The bridge now adds kaptyorka's missing Claude Code hooks at start, so the four new hooks (PreToolUse, PermissionRequest, StopFailure, SessionEnd) reach machines that joined earlier; `leave` removes them. The two that run on every tool call start with a shell check, so no kaptyorka process starts while no session is in overnight mode.
- Not yet tried for real: the crash restart with `claude --resume` in tmux, the "continue" after a usage limit or an API error, the manager passing a rule clash on to the person, and macOS. A real Claude Code 2.1.330 run in a sandbox (temp folders, no hub) blocked a script on the hardware list by default and ran it after "you may move the motors".
- **Open sessions keep working after kaptyorka updates under them.** A session started before an update answered "Internal server error" to every kaptyorka tool call until `/mcp` reconnect: its `kaptyorka mcp` loaded part of its code only at the first tool call, so after the update that part came from the new version, next to the old version already in memory, and failed (`module 'kaptyorka.paths' has no attribute 'MANAGER_TMUX'`). Auto-update did this on every teammate's machine. Now the tool server loads all it needs at start, so an update on disk cannot break it; if a call still fails while a newer version is on disk, the session hears "kaptyorka was updated on this machine; run /mcp and reconnect kaptyorka" instead.
- **A new hub version starts the manager at once, even after crashes on the old one.** The crash streak survived updates, so after 0.9.29 the manager waited up to an hour for 5 crashes caused by the old version's bug. The first start of a different version now forgets the streak (the "does not trust the folder" stop and the refused-launch limit stay).
- **A manager that has run for 5 minutes clears its crash streak while it still runs**, not only when its run ends, so Settings stops showing old crashes and a later crash starts counting from one.

## 0.9.29

- **The manager stays up when a team machine runs it.** The hub took the manager's session reports only from an admin's own bridge, while the bridge that runs the manager can be the hub key's person's, a team machine. That bridge's reports were dropped, so the hub saw the manager only at its first tool call, judged it ended a minute and a half later, and started it again and again; messages to it were not pushed. Now the bridge that runs the live manager worker always reports its session. (Older versions had the same gap; a manager that went to sleep hid it.)
- A launch order that comes before the bridge's first heartbeat answer (just after a start or a hub restart) waits for that answer instead of being refused with "this account belongs to None"; the hub offers it again within a minute.

## 0.9.28

- **A short hub guide at session start, so nobody has to remember `/hub team`.** In a personal folder the agent hears, at most 500 characters, built on this machine alone (no hub call): only when the request touches a team project, a teammate, a team machine or the hub, suggest `/hub team <project>` (with the person's own projects) or `/hub team` to coordinate, once, and `join_team` only after a yes; nothing for personal work. A team project's start brief gets one line (private work: `/hub off`), a coordinator's the "name a project for notes and work" line, and an off session only that it is off. Codex says `$hub`. Delivered by the tools' own user-level hooks: Claude Code's and Codex's `SessionStart`, OpenCode's plugin system text, and a new Cursor `sessionStart` hook in `~/.cursor/hooks.json` (written at bridge start, removed by `leave`).
- **Machine warnings on the Machines page, for everyone.** Each warning (old kaptyorka, bridge offline, hooks missing, no tool logged in, no tmux, a failed or unattended worker) is an amber chip on its account's row, full text on hover, a click shows the fix with Copy. No tool logged in has no chip of its own: the "not logged in" tool tag opens it (and "No agent tool" says what to install). A **Warnings N** chip filters to them, and the count shows beside Machines in Settings. Members see only their own accounts, workers and the team machines they can use (the hub filters `/api/warnings`, which members may now call); admins see all. Home is unchanged.
- **The manager tells a person when their machine runs an old kaptyorka.** Half an hour after the hub starts a new version, each machine still behind is sent to the manager once per hub version, with a short fixed reason (auto-update failed, timed out, not installed with pipx, no newer release found, off for this machine, bridge offline, not run yet), never the raw error. It wakes a sleeping manager; with the manager off nothing is sent. The manager messages that person (their session, else their page; the admins for a team machine) with `kaptyorka update` to run there. The bridge now reports a failed auto-update's reason to the hub, and counts "already the latest" as a failure, so it tries again later. The manager and admin sessions can now write to any person's page with `send(to="web:<name>")`. The manager's `CLAUDE.md` is written again whenever its text changes, not only with the rules.
- **Auto-update is on for admins' machines too.** Before, a machine owned by an admin did not update itself when the hub got newer; now every machine does unless its setting says off.
- **The manager no longer gets stuck for an hour after waking soon after its last run.** Each worker start now gets its own systemd scope name (`kaptyorka-worker-<name>-<random>`): the old fixed name was still held by the last run's scope while it stopped (up to 90 s), so `systemd-run` refused the start. A start the bridge refuses before any session runs no longer counts toward the manager's two launches an hour; three refusals in an hour still make it wait.
- **The manager stays up.** It runs as an interactive Claude Code session in its own tmux session (`kaptyorka-manager`) instead of `claude --bg`, so Claude Code's background service no longer stops it after an idle hour or when memory runs low. When its session ends anyway, the hub starts a new one on its next tick, without waiting for a message; the `asleep` state is gone. Before a new manager starts, the bridge ends the old one, so there are never two. Attach with `tmux attach -t =kaptyorka-manager`. The hub machine now needs tmux. In an untrusted folder it fails as untrusted, as before.
- **Only crashes slow the manager's restarts.** Normal wake-ups never wait (the old limit of two launches an hour is gone). A start that never showed up, or ended within about 3 minutes, waits 2, 4, 8, 16 minutes before the next try, then once an hour after 5 crashes in a row, and Settings says why with the last error.
- **The manager can use subagents** (the Agent tool) for its own longer jobs, one per job, so it stays free for messages. A subagent gets only the manager's tools (checked on Claude Code 2.1.329). Its instructions say: answer quick things at once, say "working on it" otherwise, send code work to the person's own machine, and keep open tasks per person in its own state note (`state("manager")`), which only it can read.
- Worker scopes are started with `--collect` again, so a failed scope does not stay in `systemctl --user --failed`; a systemd that does not know the option gets one retry without it. A worker's scope is never stopped: it can hold Claude Code's shared background service or the tmux server, and with them other sessions.
- Not yet tried for real: the session hub guide in Codex, OpenCode and Cursor (fakes only; Claude Code was probed for real); a real manager acting on the old-version notice; a real pipx failure; the manager on the real hub machine, its slow test, and a run of an hour or more.

## 0.9.27

- **`/hub` works in OpenCode 2, with a hub indicator.** OpenCode 2's terminal UI gets kaptyorka's TUI plugin (`~/.config/opencode/plugins/kaptyorka-hub/tui.js`): `/hub`, `/hub on`, `/hub off` and `/hub team [project|off]` run `kaptyorka hub` for the open session and show the answer as a toast, and the prompt footer shows **hub**, **hub off** or **hub ✗** like Claude Code's status line (`kaptyorka hub-state opencode:<session id>`). On OpenCode 2 the old `commands/hub.md` is removed (only kaptyorka's own), since OpenCode would list it next to the plugin's `/hub`; OpenCode 1 is unchanged. A folder or file of that name that kaptyorka did not write is left alone; `leave` removes only its own. The bridge writes it at start.
- **`kaptyorka doctor` on OpenCode 2** checks the TUI plugin for `tool: opencode /hub`, and "opencode server" fails while OpenCode 2 runs without its background service (`--standalone` or the service disabled), with `opencode service start` as the fix.
- **The OpenCode 2 login check no longer starts OpenCode's background service.** It runs `opencode auth list --standalone --format json`: a stored credential counts as logged in; anything else (provider environment variables only, none, unreadable output) is unknown, never "not logged in". It waits up to 15 seconds, since it starts a private server. OpenCode 1 is unchanged.
- **The hub indicator no longer says "hub off" for a session that joined with `/hub team [project]` in a personal folder** (Claude Code's status line since 0.9.26, and the OpenCode 2 footer). The joined project counts, as for the bridge; `/hub off` still wins.
- **`kaptyorka login-copy` copies Codex and OpenCode logins too.** Without `--tool` it copies every tool logged in on this machine, one line per tool (logged in there, already logged in there, not installed there, or failed), and exits 0 unless one failed; `--tool claude|codex|opencode` copies one, and `--tool claude` behaves as before. Only the login file is copied (Codex's `auth.json`, OpenCode 1's `auth.json`), the same way as Claude Code's: over ssh stdin only, saved readable only by that user, checked there afterwards. OpenCode 2 is copied with `opencode auth export` here piped over ssh into `opencode auth import` there, each through a private server that ends with the command; a logged-in target means one with a stored credential (provider keys in the environment do not count). OpenCode 1 and 2 cannot be mixed and say so in one line. Linux only; Codex with its login in the system keyring says there is nothing to copy. The README notes that both machines then share one login.
- Codex logged in with an API key now counts as logged in (its status says "API key configured", not "Logged in"), so the machine list no longer shows it as unknown.
- A message the Codex app-server refuses shows "the agent tool refused the message" instead of "the session isn't reachable".
- When `$hub` cannot run in Codex, the line says `$hub`, not `/hub`.
- **A renamed computer's sessions take its new name.** The machine name saved at join (`user@host`) used to stay after the computer got a new host name, so Claude Code sessions (and every other tool's) still showed `user@<old host>`. The bridge now renames it to `user@<new host>` at start and on each heartbeat, saves the config and logs it; the hub renames that device's sessions on the next heartbeat, with the same token and device, so nothing is duplicated and no access is lost. Cursor folders switched off with `/hub off` (or joined with `/hub team`) stay so under the new name. A name chosen with `--name` stays unless it has the form `<this account>@<host>` (as `fleet add` gives), nor is the name of a machine on the shared 0.1 token (the hub's heartbeat answer now says `legacy`; with an older hub, only a config with a signing secret is renamed).
- Not yet tried for real: OpenCode 2 login copy (checked against OpenCode's source and with fakes), and matching OpenCode 2 windows to their sessions. `/hub`, the footer indicator and message delivery were run against a real OpenCode 2.3.2.

## 0.9.26

- **The manager keeps the team's knowledge.** It maintains the team notes `team`, `machines`, `projects` (one line per team project), `glossary` and `decisions` by itself: it reads before it writes, merges, replaces stale lines, and dates and sources each fact. It asks the people working on a project when something is unclear or the project's note is missing or about 14 days old, proposes rules for what repeats (never edits them), and never stores secrets, personal matters or non-team projects. Once a day after 4:00 (hub machine time) it gets a knowledge digest: changed notes (author and a size hint, never the text), new and removed people, team machines, machines and projects, the sessions working in each team project, and finished workers, capped at 4,000 characters. A project note written or a worker finished sends a short notice, at most one per 10 minutes. These never wake a sleeping manager. The manager may now read and write the notes of every registered project (`projects` lists them all with the role `notes`); members' rights are unchanged.
- **OpenCode 1 no longer depends on the shell alias.** Its TUI listens (so the bridge can find and push to it) only when started with `--port`; OpenCode 1.19 ignores `server.port` in `opencode.json` for the TUI. kaptyorka now writes an `opencode` wrapper to `~/.local/bin` that adds `--port 0` to the TUI, when that folder comes before the real binary on a login shell's PATH, and falls back to the alias otherwise. The bridge sets it up at start for machines that joined earlier; `leave` removes it; hub-started OpenCode workers start through it too.
- **`kaptyorka doctor` fails "opencode server"** while an OpenCode window runs without its local server: "OpenCode is running without its local server, so the hub can't reach it -> close it and start it again from a new terminal". `--fix` never closes it.
- **Made-up OpenCode session ids are refused.** `KAPTYORKA_OPENCODE_SESSION` must look like OpenCode's own (`ses_...`), so no identity is made that nothing could deliver to. A push that fails now keeps a short reason (the session isn't reachable, is off the hub, its tool refused it, or the tool only pulls; never the bridge's raw error), and the page shows **Not delivered** under your last message (reason on hover) until the session reads it, for every tool.
- **OpenCode's login check no longer warns by mistake.** It reads `auth.json` and counts both credentials and provider environment variables in `opencode auth list`; finding none is "unknown", never "not logged in".
- **A session takes its machine's current name.** A session kept across a machine's new name (OpenCode keeps its session ids for good) is renamed like a new session would be, and an OpenCode shim reads the machine's name from the config again instead of keeping the one it started with.
- **A copy of a project counts as the project, by its git remote.** A session in a folder whose name is no team project (a worktree or branch copy such as `proj-a-fix-login`, a submodule) counts as a registered project when one of the folder's git remotes is that project's `--repo`, whatever the URL's scheme, user, port, `.git` ending or host case. Before, such a session was silently left off the hub. The match is made on the machine: the hub sends only a fingerprint of each registered repo, and the machine reads its own git config (cached per file, no git process); nothing of other folders leaves it. A folder named after a team project keeps that project; with two projects matching, neither does; projects without a repo match by name only.
- **`/hub team [project]`: put one session on the team from any folder.** `/hub team` makes the session a coordinator: on the hub as your session with no project, labelled `coordinator` on Home. It reaches every session you may reach (your own, team machine sessions in your projects), and they can answer it; project notes, state and `work` name the project, and your role decides. `/hub team <project>` gives it that project instead (your role in it and the project registered, checked by the hub first), as if it ran in the project's folder. `/hub team off` leaves. Agents can also use the new `join_team(project)` tool, only when the person asked. The choice is per session, kept on the machine until the session ends; nothing of the folder (name, path, git, files) goes to the hub.
- **A refused call from a personal folder says how to join.** "This folder isn't a team project, so nothing from it goes to the hub. If this session works for the team, run /hub team (to coordinate across projects) or /hub team <project> (you have: proj-a, proj-b), or open the agent in your copy of that project." It lists only your projects, and tells the agent to offer it to you, never to switch on its own.
- **A session may answer one that messaged it.** For 24 hours after a session wrote to another, the other may reply by name or #id, even when it could not reach or list it otherwise. Before, a team machine session could not answer a member session from another project ("no session named #… that you can reach"). It never adds anyone to `who`; a team machine hidden from the person still blocks it both ways, and closing a door between the two ends it.
- **`/hub on` and `/hub off` in every tool.** OpenCode gets `/hub` (its plugin runs it for the right session and shows the answer as a toast, also when a chat starts), Codex gets `$hub` (a skill its prompt hook answers, plus a line at session start saying whether the session is on the hub), and Cursor gets `/hub` (a skill its new `beforeSubmitPrompt` hook answers; in Cursor it switches the folder). All run the same `kaptyorka hub` as Claude Code, so `/hub team [project]` (`$hub team` in Codex) works in each too. An off session of any tool is never reported by the bridge or the Cursor shim, gets no pushed messages, and its hooks and kaptyorka tools stay silent. `/hub` also says when a folder that is not a team project keeps the session off anyway.
- The bridge installs each tool's `/hub` and hub indicator when it starts (Claude Code's status line field too), so an update brings them without joining again. `kaptyorka doctor` checks them per tool and `--fix` puts them back. The README has what each tool can show.

The choice lasts for that session, across bridge and hub restarts, and ends with it. Background sessions ignore the variable (use `/hub off` in them); workers and the manager cannot go off.
